## Main findings

**Layer 2 is green.** The release's own publish step gives the same 1237
files on one path, across three build paths, and four hours apart: our DLLs,
the launchers, `deps.json`, and the whole .NET runtime. Layer 1's two open
path channels do not reach the release (W17).

**The dependencies are now locked.** We added NuGet lock files to make sure
that both the direct and the transitive dependencies are pinned: every
package WebAPI resolves, 334 of them, with a content hash each. In locked mode,
which the release job now uses, restore fails instead of silently picking
something else. With the two follow-up fixes the locked release is
byte-identical to the unlocked one, so the lock files pin the graph without
changing a byte. This is a precondition for reproducible builds, not the
whole of it: the packages are now pinned by hash, not rebuilt from source.

**A release DLL is not a build DLL.** The version string from the tag reaches
every own assembly (W19), and the programs carry the runtime identifier in
their PDB path and an x64 flag (W20). A verifier has to use the release's own
command and version string; `dotnet build` output cannot be compared with a
release.

**What ships is decided by defaults.** Three unintended changes to the release
were found in one afternoon: an empty npm file shipped because of a glob (W18),
a setting meant for the lock files put Windows binaries into the Linux release
(W23), and a split restore wrote the wrong versions into `deps.json` (W24).
All three builds were deterministic, so reprotest alone would have passed them.
A byte comparison with the previous release caught each within minutes. That is
a use of reproducibility the plan did not have: any build change shows up as a
diff, before anyone reads a line of the change.

**File order does not reach the compiler.** MSBuild sorts every wildcard result
with an ordinal comparison (W12). The file-order run would still test code that
lists directories on its own.

## Observed, not measured

- **The release's SDK floats.** The release job installs "9.0.x", and `main`'s
  `global.json` accepts any SDK from 9.0.0 up, previews and newer majors
  included. The branch's exact pin to 9.0.120 would probably fail in that job.
- **`WebAPI.csproj` ships a Homebrew library on Macs.** Lines 38-44 copy
  `libnlopt.dylib` from `/opt/homebrew/lib` or `/usr/local/lib` into the
  output when the build machine has it. The release then depends on what is
  installed on the build machine, not only on the repo.
- **Most packages name their source.** 286 of WebAPI's 334 packages declare in
  their `.nuspec` the commit they were built from, for example AutoMapper
  13.0.1. Whether that commit rebuilds the DLL is the dependency part's
  question; the other 48 cannot even be traced that far.
- **The version Phoenix shows drops the commit.** A release built in a git
  checkout gets `+<commit>` appended to its informational version, and
  `SystemInfoService` cuts it off before displaying the version.
- **Restore reports dependency warnings** (security advisories, a version
  constraint) that are for Weel-Sandvig to act on. They are passed on to WS
  directly and not listed in this public repo.

## Corrections to earlier wording

- **"Every direct package reference names one exact version."** In NuGet,
  `Version="13.0.1"` means 13.0.1 or higher, resolved to the lowest available.
  The lock file shows it: `"requested": "[13.0.1, )"`. In practice exact, but
  only the lock file makes it so.
- **The lock-file patch's comment said `RuntimeIdentifiers` on every project
  "only adds runtime graphs to the lock files".** It also changed what the
  release contains (W23).
- **Expectation 4 in phoenix-layer2**, that the libraries in the release are
  identical to `dotnet build`'s, was wrong: the version stamp reaches them
  (W19).
- **The 15/9 clean step** missed the test project (W11). The 15/9 result stands.

## Craft that worked

- Compare every run with a known-good release, not only with its own twin.
- `pkill -f pattern` over ssh matches its own command line and kills the
  session; `pkill -f "[p]attern"` does not.
- The terminal panel's Run button sends a command to an idle tab. A shell
  started inside a tab (`fish`) makes that tab busy, so commands land in a new
  tab without the variables. Paste into the tab instead.
- `find release -type f -print0 | LC_ALL=C sort -z | xargs -0 sha256sum`
  works unchanged in bash and fish; `${REF_NAME#v}` and `( … ) > file` do not.
