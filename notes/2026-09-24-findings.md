## The big one

- The C# compiler sorts some types it generates by the machine's language
  setting. An Estonian machine builds a different Phoenix release (W26).
- Two small methods of our own code reproduce it. The compiler's own record of
  its inputs says both builds had identical inputs, so by Microsoft's own rules
  it is a bug.
- Microsoft fixed it by accident in October 2025, only from SDK 10.0.2xx. No
  .NET 9 SDK has the fix, and three similar sorts remain even in the newest
  compiler.
- Our fix is on the WS branch: `LC_ALL=C.UTF-8` in the Linux release jobs. It
  changes no bytes.

## About our method

- reprotest's second build borrowed the first build's compiler server, so our
  variations never reached the compiler (W27). The layer 1 locale, time, umask
  and PATH tests of 15/9 were not real tests (W10 rejected).
- Fix: shut the build servers down around every build. That also removed a
  10-minute wait in the time test.
- MSBuild's worker processes survive that shutdown; one lived 28 minutes. No
  later build used them. Next time node reuse is switched off.
- reprotest quietly fixes things: one CPU, timezone GMT+12, language
  `C.UTF-8`, and `HOME` inside the build folder (W28).
- Nobody has documented the build-server problem before: a method contribution
  for the thesis.

## About Phoenix's release

- A shifted clock, umask and `PATH` do not change it (W29). Neither do the
  number of CPUs, the timezone or Danish language settings.
- File permissions follow the umask of whoever writes each file (W30). That
  matters once we zip (layer 4).
- 311 dates in a web-assets file come from a Microsoft package, not from the
  build clock (W31).

## About Benedetti et al. and other tools

- They ran reprotest as we did: one machine, one user, one variation at a
  time. They did not vary the build path and never mention background
  processes.
- npm, pip, gem, Maven and Go leave nothing running, so their results do not
  have our .NET problem (T1).
- reprotest's clock shift cannot reach Go, so a green Go time test proves
  nothing (T2).
- pip fails under the shifted clock: the certificate looks expired. The same
  problem they reported (T3).
- Maven shares its cache between the two builds (T4).
- Their code has no license, so the repo keeps a download script, not the
  files.
