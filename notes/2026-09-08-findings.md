## Main finding

`9.0.120` covers **two source revisions and two compiler binaries**. The version
number identifies neither.

The two compilers are the same code: decompiled, both `csc.dll` are 1672 lines
with 12 differing lines, all metadata (commit, target framework, repo URL,
informational version). Same Roslyn version `4.12.0-3.25609.5`.

And they emit identical code. The same source built on the same path with each
compiler gave `e793b11f…` against `4ede5f51…`, but **0 differing lines**
decompiled. The difference is 70 bytes out of 4096, spread over five identity
fields:

| Byte | Size | Field |
| --- | --- | --- |
| 137-140 | 4 | the PE header's `TimeDateStamp` |
| 1597-1612 | 16 | the module's MVID |
| 1821-1824 | 4 | timestamp in the debug directory |
| 1905-1920 | 16 | PDB id |
| 2065-2096 | 32 | PDB checksum |

The chain: the compiler writes its own name into the PDB, `compiler-version:
4.12.0-3.25609.5+d0558bff…` appears verbatim in the file, and the DLL carries the
PDB's id and SHA-256. The other two fields are hashes of the content.

**Bit identity is stricter than code identity.** The consequence is hard: a
distribution that builds the compiler from source can never hit the vendor's
artefacts, no matter that the code is the same. Bit-for-bit verification requires
the vendor's own compiler binary, pinned by content.

**Precedent for a recommendation:** both `csc.dll` have embedded PDB paths
starting with `/_/`. Both Microsoft and Arch use `PathMap` on their own releases.
Phoenix has none (verified 19/8). The recommendation is therefore not a new idea,
but doing what the tool vendor does to itself.

## Lessons that belong to no single experiment

- **Determinism** is a property of the process, **reproducibility** of the
  description. The first is measured on one machine; the second requires the
  input to be declared well enough that someone else can achieve it.
- **Cross-OS is not the bar.** The definition requires the same *declared* build
  environment. Debian records it in `.buildinfo`. Our failed measurement on 7/9
  was underspecification, not an OS problem.
- **An assembly** is one PE file with IL and metadata. Roslyn produces exactly
  one per project; MSBuild produces none. It generates source, calls the compiler
  once, and copies. The `bin/` DLL is a copy of the `obj/` DLL, hence
  `rm -rf bin obj` and not just `rm -rf bin`.
- **The PE timestamp is not a point in time.** Four bytes of a hash in a field
  labelled as seconds since 1970. `86 39 3d df` -> 3,745,331,590 -> 2088-09-06.
  The field can only express 1970-2106, so two thirds of the time it points into
  the future. Determinism therefore erases the build time: if you want to know
  when, the answer has to come from an attestation beside the artefact.
- **Artefacts come in layers**: assembly, `.nupkg`, zip, OCI layer. Archive
  metadata (timestamps, ownership, file order) only bites from layer two. Today's
  green results are therefore conditional on there being no packaging step.
- **`.deps.json` carries a `sha512` for almost every dependency** (46 of 47 in a
  real Phoenix file), and the loader does not check them. To be re-checked, but
  if it holds it is a finding right next to the gap in the standards.
- In Phoenix your own build compiles **four** of around 300 assemblies in a
  release. The rest are copied bytes, compiled by another csc somewhere else.

## Craft that worked

- A fixed absolute path on all machines. `/private/tmp` rather than `/tmp`,
  because macOS' `/tmp` is a symlink.
- SDK pinned with `global.json` and `rollForward: disable`. `dotnet --version`
  **from the project directory**; outside it you get your newest SDK.
- Environment block recorded *before* the measurement, with the whole
  `dotnet --info` (not `head -12`, which hides both the commit and the
  `global.json` line), plus `command -v` and the `csc.dll` hash.
- `sha256sum -c`: our evidence files are already checksum files, so yesterday's
  file is today's test.
- `env LC_ALL=C` in everything that sorts. Measured: the same files sorted under
  `da_DK.UTF-8` and under `C.UTF-8` give two different manifest hashes.
- Never build inside the repo. The editor on the repo, the terminal on the lab.
- `pedump` (for diffoscope) and `ilspycmd` make the difference between "where"
  and "what". Without `pedump`, diffoscope falls back to hexdump on .NET files.

## Corrections to earlier wording

- **"Same source, different binary" was wrong** about the 7/9 result.
  `dotnet --info` shows that the two SDKs are built from different source
  revisions (`d0558bff3d` against `3f97250e38`). The correct wording is that the
  version number does not identify the source revision.
- **RID and the `dotnet` host were not independently ruled out** by experiment 3.
  They came along with the SDK: the RID changed from `arch-x64` to `linux-x64`
  and the host from 10.0.11 to 9.0.19. The conclusion is therefore "the SDK
  decides", not "the compiler alone decides".
- **The control with `-p:RuntimeIdentifier=linux-x64` measured the wrong thing.**
  With a RID the output moves to `bin/Release/net9.0/linux-x64/`, and then the
  embedded PDB path changes. Verified: the path became
  `/private/tmp/rb1/obj/Release/net9.0/linux-x64/minlib.pdb`. The difference was
  the path, not the RID. To isolate the RID, `PathMap` has to remove the path
  difference first.

## Caveats

- That Roslyn's deterministic hash takes in the compiler's own identity is
  inferred from the observation (same IL, different MVID). To be checked against
  Roslyn's source before it is cited as a mechanism.
- The four PDB-related fields in the byte table are identified from position and
  size, not against the format specification. `TimeDateStamp` is verified by
  offset.
- 0 differing lines is measured on **decompiled C#** from ilspycmd, not on raw
  IL. A strong indication, not proof of identical IL bytes.
- Everything is still measured on an empty class: no dependencies, no packing, no
  archives, only x64 Linux.
