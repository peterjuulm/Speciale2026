## Main finding

**The DLL carries a hash of the compiler's identity, never the identity itself.**

The compiler's commit string appears twice in `minlib.pdb` and zero times in
`minlib.dll`, neither as UTF-8 nor as UTF-16. `[V]`

The chain, measured link by link:

1. `csc.dll` declares itself in `AssemblyInformationalVersion`, a 62-byte entry
   in the `#Blob` heap: `4.12.0-3.25609.5+d0558bff…` `[V]`
2. `GetCommitHash()` in `csc.dll`, 44 bytes of IL, asks which assembly it itself
   lives in, fetches `CommitHashAttribute` by reflection and returns its `Hash`
   `[V]`
3. The string arrives verbatim in the PDB's CompilationOptions blob as
   `compiler-version` `[V]`
4. The PDB checksum in the DLL's debug directory is SHA-256 of the PDB with the
   id field zeroed. Verified byte for byte `[V]`
5. The PDB id is the first 20 bytes of that hash with the UUID v4 bits forced:
   `8f` to `4f`, `65` to `a5`. The MVID uses the same trick `[V]`

Re-check point 4:

    python3 -c "
    import struct,hashlib
    b=bytearray(open('/private/tmp/rb1/bin/Release/net9.0/linux-x64/minlib.pdb','rb').read())
    off,size=struct.unpack_from('<II',b,16+struct.unpack_from('<I',b,12)[0]+4)
    print('som den ligger   ', hashlib.sha256(b).hexdigest())
    b[off:off+20]=b'\x00'*20
    print('med id nulstillet', hashlib.sha256(b).hexdigest())
    "

It must give `98bcbc158ee51d8f656f9a4a919e54e5f639b0bd9564de0bfdb134f6016f7500`,
and that number appears in the DLL's debug directory, entry of type 19.

That explains yesterday's 70 differing bytes spread over five fields, and not one
byte more: there was no text string to differ in, only hashes.

**And it makes the channel closable.** If no PDB is written, neither the CodeView
entry nor the checksum entry exists, and the compiler's identity has no way into
the artefact. Not tested, see "Tomorrow".

## Microsoft's SDK is platform-specific

Yesterday's prediction that `csc.dll` was the same across RIDs was wrong.
Measured on archives downloaded from `builds.dotnet.microsoft.com` and verified
against the SHA-512 in Microsoft's `releases.json`:

| SDK 9.0.120 | `csc.dll` sha256 | size | `.text` | Machine | Roslyn commit |
| --- | --- | --- | --- | --- | --- |
| Microsoft osx-arm64 | `1824569732a63f5d…` | 132,096 | 102,400 | `0xec20` | `fc52718e…` |
| Microsoft linux-x64 | `644a4d336dcd11a7…` | 121,856 | 91,648 | `0xfd1d` | `fc52718e…` |
| The Arch package | `1b7543aa709363b6…` | 121,856 | 91,648 | `0xfd1d` | `d0558bff…` |

All three are ReadyToRun images: `ManagedNativeHeader` carries the signature
`RTR\0`. `csc.dll` is therefore not pure IL, but IL plus precompiled machine code
for one architecture. That is why the ARM64 build is 10,240 bytes larger. `[V]`

The `Machine` field is not an architecture code, but the architecture XOR an OS
constant, so Windows refuses to load a foreign image as native code:

    AMD64 0x8664 ^ Linux 0x7B79 = 0xfd1d
    ARM64 0xAA64 ^ Apple 0x4644 = 0xec20

The constants are in `dotnet/runtime`, tag `v9.0.19`,
`src/coreclr/inc/pedecoder.h` lines 96-112. `[V]`

But the source revision is the same. `.version` in both Microsoft archives says
`3f97250e38169d4fede59f43029c6d987c015eb4` and servicing number
`9.0.120-servicing.26371.12`; only the RID line differs. And both `csc.dll` carry
the same Roslyn string. `[V]`

So the prediction for macOS still stands, but for a different reason than
yesterday: the compiler binary is a different file, but the declared identity is
the same, so the output should come out `4b3808d1…`, identical to `ubuntu-vm`.
`[I]`

That gives a sharper wording than yesterday:

> Yesterday: two compilers with identical code and different metadata strings gave
> different output. The prediction now: two compilers with different bytes and
> different machine code, the same metadata string, give identical output.

It is not the compiler's bytes that decide the output. It is the identity the
compiler claims about itself.

## The macOS route

`dotnet-install.sh` is the only way to hit 9.0.120 on a Mac. `[V]`

Homebrew's `dotnet` formula builds from source. The source URL is
`github.com/dotnet/dotnet`, the same unified source tree the Arch package uses,
with `cmake`, `pkgconf`, `rapidjson` and `llvm@20` as build dependencies.
`dotnet@9` exists, but is at 9.0.121. The cask `dotnet-sdk` is Microsoft's real
`.pkg`, but only in the newest version (10.0.401).

The verification is `3f97250e38`. Microsoft builds one source revision for all
platforms, so the commit field is RID-independent. If Peter's Mac says something
else, it is a different build.

reprotest cannot run on macOS: no Homebrew formula, and the module calls
`unshare`, `setarch`, `domainname`, `disorderfs` and `faketime`. The man page
itself says only Debian- and RPM-based packages are supported. The Mac can
therefore contribute to experiment 1 and 3, not to the axes. `[V]`

## Lessons that belong to no single experiment

**The provenance sits in the PDB, not in the assembly.** The PDB is 10,352 bytes
against the DLL's 3,072, 3.4 times larger for a two-line class. `#Blob` is 96
percent of the file and contains 164 reference assemblies named by name and MVID.
The DLL names one `AssemblyRef`, because it only needs `System.Runtime` to run.
`[V]`

The consequence: if you want to know what a build consisted of, which references,
which source files with which hashes, which compiler, the answer is in the
debugging file. Build without a PDB, or publish the binaries without the PDBs,
and the machine-readable record no longer exists.

**ECMA-335 stops where reproducibility begins.** Searched through the 6th edition
(June 2012): zero hits on "Debug Directory", "IMAGE_DEBUG" and "Portable PDB".
"reproducible" appears three times, all three about floating-point precision
(p. 317). The metadata format and the PE extensions are standardised; the debug
directory, `CodeView`, `PDB Checksum`, the `Repro` entry, the Portable PDB format
and `CompilationOptions` exist only in Microsoft's own documents, which they can
change without a revision. `[V]`

That rhymes with the starting point on the PEMS side: the standard describes the
instrument, while the mechanism that decides identity sits outside it.

**Microsoft itself compares commit hash, not version number.** `GetCommitHash()`
exists because the compiler client and the `VBCSCompiler` server have to decide
whether they are the same build before they talk. They have therefore concluded
themselves that `9.0.120` does not identify a binary. It is still a string
comparison, not a hash of bytes, one step further than compliance documentation
normally goes, and one step short of what we are arguing for.

**A PDB is not a PE file.** `minlib.dll` starts with `4d 5a` (`MZ`);
`minlib.pdb` starts with `42 53 4a 42` (`BSJB`). The PDB is pure metadata with no
container, because it is only read and never loaded as code. `objdump -p` answers
"file format not recognized" on it, and that is the right answer. `[V]`

In the DLL, `BSJB` sits at offset 596, and the twelve bytes just before it are
the whole program:

    0e 1f 2a 2a 1e 02 28 0c 00 00 0a 2a    the IL code, 12 bytes
    42 53 4a 42                            the metadata begins, 1212 bytes

The ratio of description to code is a hundred to one.

## Craft that worked

`ildasm` exists for linux-x64 as a NuGet package,
`runtime.linux-x64.Microsoft.NETCore.ILDAsm`. It gives the same manifest format
Microsoft's documentation shows, and replaces the hand-written PE parsing. Two
caveats: use `-caverbal`, or attribute values come out as hex, and use `-` rather
than `/`, which the Linux build's argument parser does not understand. It cannot
print 64-bit hex: `.imagebase`, `.stackreserve` and the table bitmask come out as
`0x%016I64x`.

`objdump -p` says on its own "This is a reproducible build file hash, not a
timestamp" about `TimeDateStamp`. That is an independent tool, GNU binutils, not
Microsoft's, treating the field as a hash. Worth citing. It does not know the
entry of type 19 and calls it `Unknown`.

`strings -a -n 2` on the PDB gives the whole CompilationOptions block. Default
`strings` requires four characters in a row; with two, the key-value pairs each
get their own line.

`grep -abo BSJB fil.dll` gives the byte offset of the metadata with no parsing.

## Caveats

The macOS prediction is `[I]`. Neither of us has run a build on a Mac yet.

The order inside `csc`, that `MVID` and `TimeDateStamp` are stamped before
`PDB id` and `PDB checksum`, is an inference from the fields having to be patched
after a content hash. What was measured is that the DLL contains the PDB's id and
checksum.

`GetCommitHash()` sits in `BuildProtocolConstants`, that is the protocol between
compiler client and server. It is not proven that the PDB writer uses the same
reader. That the string travels from `csc.dll` to the PDB is measured directly.

Whether the `Repro` entry survives `DebugType=none` is unknown.

The channel via the reference set is not tested. That 164 assemblies with MVID
appear in the PDB's `#Blob` is measured; that a different targeting pack therefore
changes the DLL follows from the chain but has not been checked.

The Homebrew measurements are read out of the `formulae.brew.sh` API, not out of
a Mac. What Peter actually has installed we only know when he runs
`dotnet --info`.
